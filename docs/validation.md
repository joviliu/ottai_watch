当前表盘安装状态：Mi Fitness `FaceDesignerFragment` 解压与工程文件检查成功，但 `designer_license` 授权接口仍返回 HTTP 404。独立本地 SPP 正常认证通过，`replace` 本项目固定 ID 后已收到 `UPLOAD 100%`、`INSTALL_OK` 和 `DISCONNECTED`；用户确认修正 Lua 入口后的表盘正常绘制。`INSTALL_OK` 自身仅表示上传流程及激活请求发送完成，此处绘制成功另有用户目视确认。

黑屏根因已确认：打包器所谓 `sentinel` 实际是 Lua anchor payload 的资源索引，原默认 `n-1` 指向本项目趋势 PNG，实际 `lua/main.lua` 当时在索引 14。`build.py` 现按文件名查找 `main_index`，并断言解包后的入口仍指向主脚本；不能固定写死索引 14。

为安装器临时 `disable-user` 后，系统清除了镜像和 Mi Fitness 原有通知访问；现已恢复此前获授权的镜像通知监听与 Mi Fitness `NotifySyncService`，两应用运行状态回到 `default`。镜像手机 `MainActivity` 增加启动时 `NotificationListenerService.requestRebind`，但它不能代替用户通知授权。后续恢复流程必须同时核对通知访问、监听绑定及最新 Ottai 数据进入，避免拿旧缓存继续验收。

私有文件传输实测发现 `adb exec-in ... dd` 可能产生空文件或截断；已改用 `adb shell -T run-as ... sh -c 'cat > ...'` stdin 写入，并在 Python 内回读比较 SHA-256。再次启动安装器采用 `am start -S`，必须先确认上一轮操作已经 `DISCONNECTED`。详细步骤见 [临时 SPP 安装器](../tools/spp-installer/README.md)。这些验证不公开凭据、原始健康日志或设备标识。

目前真实趋势为水平箭头；斜向及其他方向已做映射测试，但尚无真实方向变化序列的目视验证。公开记录只保留结果及耗时，不保存真实血糖值、原始通知或医疗时间线。

**开发版基本验收通过。** 连续两轮锁屏自然更新的文件导出与 ACK 已验证，通知到 ACK 分别约 9.8 秒和 9.7 秒；源测量时间相隔 5 分钟，数值有变化。用户确认最新屏显的数值、水平趋势与原始时间正确，并正常返回表盘，未报告明显闪屏或卡住。该结果证明无需手动打开的短暂唤起策略在这两轮完成了文件更新和表盘显示，不证明真正常驻后台、精确屏显耗时或长期可靠性。
