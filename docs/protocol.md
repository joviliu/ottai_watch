# 数据与时序

```
Ottai com.ottai.tag 通知
  → OttaiMetadataListener → Reading / ReadingStore
  → BridgeService → Mi Fitness Wearable SDK → 蓝牙
  → Vela system.interconnect → model.js → 展示 / 缓存 / ACK
```

`sourceAt` 是通知正文 HH:mm 对应的测量时间，依据通知原始时间锚定日期并处理跨午夜；`receivedAt` 才是手机接收时间。不要用到达时间覆盖测量时间。拒绝乱序、明显未来、非法单位和值；未提供趋势时显示 `?`，不要推测。

下列数据为合成示例，不是用户读数：

```json
{
  "type": "glucose", "version": 1,
  "value": 6.8, "unit": "mmol/L", "trend": "↗",
  "sourceAt": 1792972800000, "source": "ottai_notification",
  "receivedAt": 1792972805000,
  "history": [{"time": 1792972800000, "value": 6.8}]
}
```

`system.interconnect.send({data: ...})` 的 `data` 必须为 **Object**。接收事件的 `event.data` 才是 JSON 字符串；把发送端 data 改为 JSON 字符串会触发类型错误。

手表消息类型还包括 `request_latest`、`ack` 与 `face_export`；以实际 `index.ux` / `BridgeService.java` 为准。ACK 包含对应帧的 `sourceAt`，手机只承认当前帧的回执。普通 `ack` 仍只按 `sourceAt` 匹配，不能用于判定同时间更正的文件发布完成；自动同步以 `face_export` 的完整身份为准。SDK success 仅说明传输调用成功；首次当前帧 ACK 和最近 ACK 分开记录。ACK 说明应用处理过该帧，不能证明屏幕在用户未观察时实时可见。

手机保留最多 24 个真实点；曲线不跨越超过 10 分钟的缺口。手表每分钟只更新前台年龄文本；进入、连接恢复时各请求最新帧。Vela 应用退后台时的运行与送达受固件限制，因此当前实现不能承诺表盘状态下每 5 分钟后台更新。重新打开后先显示缓存，数秒内同步最新数据是已观察到的行为。

## 表盘文件接口（自 0.1.8 起）

当前 Android 0.1.11 增加短时 CPU 执行保障和唤起冷却修复，RPK 0.1.9 试验未通过，恢复包 0.1.10 复用 0.1.8 逻辑、已覆盖安装且两次旧测量自动写入已确认，回退后表盘原始时间和正常返回已由用户确认；新测量周期尚未验证，表盘保持 0.1.10，文件格式与同步身份不变。当前单款表盘沿用此接口；未来独立 ID 的其他风格也可共用文件与同一 RPK，其外观实测状态单独记录于 [validation.md](validation.md)。

```
Vela 合法帧 → face-export.js → system.file 双槽文件
                              ↓
                    Lua frame.lua 校验 → main.lua 显示
```

应用写入 `internal://files/ottai-face-0.txt` 或 `ottai-face-1.txt`。槽位为 `floor(sourceAt / 300000) % 2`；同一测量时间重复发送写同一槽。文件使用 ASCII、末尾恰好一个换行：

```
OTT1|sourceAt毫秒|一位小数数值|趋势名称|十进制Adler32校验值\n
```

校验范围是 `OTT1|sourceAt毫秒|一位小数数值|趋势名称`，不含最后的分隔符、校验值和换行。趋势名称为 `unknown`、`up`、`up_right`、`flat`、`down_right`、`down`、`up_fast`、`down_fast`。缺失或无法映射的趋势使用 `unknown`，不根据曲线推断方向。

Lua 每个文件最多读 129 字节，接受的完整记录上限为 128 字节；检查格式、校验和值域、趋势白名单、时间及明显未来值。从两个槽选取测量时间最新的合法记录；部分写入、损坏、无文件或更旧数据均保留最后合法读数。双槽用于降低一次写入打断时丢失最后读数的风险，不是跨进程事务保证。

表盘只读本包的候选映射：

- `/data/quickapp/files/com.example.glucosewatch6/`
- `/data/quickapp/file/com.example.glucosewatch6/`
- `/data/files/com.example.glucosewatch6/`

这些路径来自现有 Lua 表盘/运行时参考；当前 Watch 6 已由用户目视确认读到导出数据，尚未单独定位命中的具体候选目录。应用仍通过官方虚拟 URI 写入，不借用其他应用的包名或读取其数据。

### 完整读数身份与写入确认

`face_export` 包含 `sourceAt` 和 `frameKey`。身份格式为：

```
sourceAt毫秒|规范数值字符串|原始趋势字符
```

JS 使用解析后的 Number 字符串；Java 使用 `BigDecimal.valueOf(value).stripTrailingZeros().toPlainString()` 生成对应形式，整数不保留 `.0`。这里的趋势是原始箭头字符，而不是文件内的 ASCII 趋势名称。确认身份与用于显示的一位小数文件格式是两层契约，不能用单独的测量时间代替完整身份。

手机只接受与当前读数完整 `frameKey` 相同的导出回执，并保存 `faceExportKey`。同一测量时间的数值或趋势更正会得到新身份，旧回执不能使该更正被误认为已导出。

发布器同时最多执行一次文件写入，另保留最新的 pending 帧。旧写入完成时若已有不同身份待发布，会先写最新帧，不确认旧帧或触发其自动退出。完全相同且已经写入的身份可省略重复 I/O，但仍回报当前帧；重复帧附带的自动返回标志也能被保留。

`face_export` 证明文件 API 曾报告该身份写入成功，**不证明 Lua 已读取或屏幕已显示**。表盘显示原始测量时间，10 分钟及以上标记 `OLD`；读取旧缓存不会刷新它的测量时间。

## 显示分段颜色

新增颜色仅为表盘渲染规则，不改变文件格式、完整读数身份或同步时序。按有效的一位小数显示值 `v`：`3.9 <= v <= 7.8` 紫 `#924ff7`，`7.8 < v <= 12.0` 黄 `#ffd60a`，其余红 `#ff453a`。数值和趋势同步着色，旧数据仍保留原始时间与 `OLD`，在对应色系中变暗。该用户自定义显示分段的升级/实机状态见 [validation.md](validation.md)。

## 自动同步策略（手机 0.1.11 / RPK 自 0.1.8 起）

隐藏镜像应用的两轮被动更新观察中，手机均收到新通知并发送，但未收到对应的 `ack` 或 `face_export`，因此不能保证被动后台持续写入。0.1.8 自动唤起策略的两轮短锁屏验证完成导出和 ACK，通知接收到 ACK 约 9.8/9.7 秒，用户确认屏显与正常返回；它只是历史连通性基线，没有先确认 Home 后的后台状态。后续实际发现 HyperOS Greezer 会冻结仍有前台服务和常驻通知的手机进程，详见 [后台排查](background-running.md)。这些耗时不是精确屏显延迟，也不是长期后台保证。

0.1.10 曾在重启恢复后单轮自然更新完成约 9.8 秒文件回执。本轮省电设置调整后的复核中，两轮通知处理延迟约 5/10 ms，但第一轮由用户手动打开手表应用才导出，只有第二轮有自动唤起与约 9.8 秒导出，不能合称两轮自动通过。恢复缓存或解锁后补收不计自然周期。手机 0.1.11 + RPK 0.1.8 组合此前已完成恢复补传及三个镜像持续后台的正常自然周期文件导出；前两轮屏显和自动返回已由用户确认。

开发版手机增加默认关闭的“表盘自动同步”开关。启用后先正常发送，8 秒内没有当前完整身份的文件写入确认时才请求启动镜像应用，再发送带 `watchfaceSync: true` 的帧。

手机用 `faceSyncKey` 绑定待同步会话的完整读数身份，不再依赖一个固定时长窗口。对应身份的导出回执、通过手机“打开手表应用”按钮主动查看，或新帧身份到达都会清理旧会话；若设备启动延迟但仍是同一待同步身份，后续发送仍带自动返回标志。

表端保留 `syncReturnPending` 意图，直到最新待发布帧完成。新合法帧接受前会取消已有退出定时器；重新排定的约 400 ms 退出回调再次核对当前完整身份，避免旧写入成功后的定时器打断后来的更正写入。`onHide` 清理退出定时器和返回意图。没有待同步返回意图的普通查看不自动退出；写入失败时保留错误与旧读数，不退出并伪装成功。

唤起策略限制为仍新鲜的当前读数。手机 0.1.11 的 60 秒冷却仅限制同一完整 `frameKey` 的重复唤起；新的测量时间或同时间的数值/趋势更正不会被上一身份挡住。启动回调也核对会话身份，过时回调不清理较新会话。

新读数/发送尝试持有至多 20 秒的 `PARTIAL_WAKE_LOCK`，同身份持有时不续期；匹配当前完整身份的 `face_export` 即提前释放，服务停止也释放。超时仍未送达时，后续重连或发送可再申请窗口，不是一个读数终身只能执行 20 秒。该窗口保障新通知已进入进程后的发送与延时兜底，不能解冻厂商已冻结进程。监听器断开时请求重绑，有新数据而服务不在时尝试恢复前台服务，均不能替代通知授权。

没有秒级传感器轮询。这个方案的含义是**无需手动打开，必要时自动短暂打开后返回**，不能称为应用始终隐藏的常驻后台更新。严格后台验证状态见 [后台排查](background-running.md)。真实趋势目前仅观察到水平箭头，其他方向为映射测试；对其他手表页面的影响、断连恢复、AOD、长期稳定性和耗电尚未完整验收。

## RPK 0.1.9 试验撤回与恢复包

[0.1.9 试验](../releases/watch-0.1.9/README.md) 已安装，但未通过验收、不推荐使用。它曾将主 UI 延迟约 2 秒，并在实时同步时隐藏至导出/返回；手动测试出现黑屏后才显示主 UI，透明窗口没有透出表盘。随后两轮自然自动周期手机已接收新帧、发出 `FACE_WAKE` 且 SDK accepted，仍没有 `face_export`，用户未见数据更新；镜像未被厂商冻结，具体失败原因尚未定位。

为恢复功能，源码已回到原 0.1.8 的入口与 UI 逻辑，仅将 RPK 版本递增为 [0.1.10 / code 11](../releases/watch-0.1.10/README.md) 供覆盖安装；已确认安装 code 0，两次旧测量自动写入已确认，回退后表盘原始时间和正常返回已由用户确认；新测量周期尚未验证。手机 0.1.11、表盘 0.1.10、完整身份与双槽文件契约不变；原 0.1.8 的三个自然周期不算恢复包已验收。试验差异保存在 [implementation.patch](../experiments/watch-transparent-0.1.9/implementation.patch)，后续调查见 [调研记录](silent-sync-research.md)。

恢复包安装后已重启手机镜像以重建 SDK 连接，随后 Home/锁屏。旧帧恢复发送和同一原始测量时间的趋势状态更正分别在约 9.86/9.85 秒完成文件导出、CPU 早释放并有 ACK，说明这两次自动写入链路恢复；它们不是两个新自然周期。上游时间尚未推进，用户已确认回退后的原始时间显示和正常返回，新的自然测量周期尚未验证，不更新原始测量时间来伪装新鲜数据。
