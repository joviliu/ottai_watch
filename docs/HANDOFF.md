- 手机 0.1.4 / versionCode 5，手表 0.1.4 / versionCode 5 是实机基线；用户已确认数值、趋势和曲线布局正常。
- 手表已覆盖升级至 0.1.5 / versionCode 6，仅放大提亮图标；用户已确认视觉符合预期。手机继续 0.1.4。
- 保留旧读数及其测量时间；进入应用自动同步，不在存在缓存时清空成 `--`。
- 跟随 Ottai 约 5 分钟更新；优先省电，不做秒级传感器轮询，不强制唤起应用。
- 手机桌面图标已有自定义图案，本轮用户只要求手表图标更大、更醒目圆形背景。
- 用户期望上滑「小部件」快速查看；找不到开放接口时，考虑按「极简风大数字」布局重绘表盘，只需数值与方向箭头，不需曲线。
- 2026-10-26 补充：小部件/表盘必须在不手动打开「血糖镜像」时随 Ottai 数据变化。只读取上次打开主应用留下的缓存不算完成；至少验证两个更新周期。

## 最小验证

1. `sh tools/test.sh`：纯 Java 通知解析 + Node 帧/互联测试。
2. 构建 APK、RPK 并检查版本/签名一致；如只更新手表图标，可保留手机 0.1.4。
3. 保持 USB 和 Mi Fitness 连接，安装时手机需由用户解锁。
4. 手表冷开/重开，确认缓存未变成新时间、随后新帧有对应 ACK。
5. 最终由用户实际看表确认显示；不能把 SDK 成功或 ACK 说成已经目视验证。

## 尚待解决

- 先读 quick-view-research.md。公开 JS 应用路由能力不等于固件的系统小部件注册能力；编译器支持某字段也不等于手表支持。
- Lua 表盘可以绘制 UI，但需要证实应用沙箱数据如何被表盘读取、隐藏时如何更新。不要硬编码未经验证的 `/data/...` 路径。
- 原厂「极简风大数字」未作为可编辑工程导出；不能将仿布局设计称为对原厂包已完成改造。
- 自定义表盘须使用独立 ID，先验证打包/解包，再安装；不要覆盖固件预装表盘。

## 本地不在仓库里的内容

原环境有 `.sign` 私钥、真实时序日志、原国行健康应用回退包和已配对设备。这些不应进入公开仓库。迁移签名依照 signing.md；设备序列号每次 `adb devices` 获取，不写进源码。缺少私钥不影响安装仓库内签好的基线包，但不能签出可覆盖旧版本的新包。
