# Ottai Ultra：Redmi Watch 6 Lua 表盘

原创 432×514 表盘，采用上方大圆点时钟、下方稀疏点阵血糖及日期、电量、心率。**本轮只有一个表盘，ID `8670260101`，名称 Ottai Ultra，直接覆盖此前同 ID 版本。** 不发布第二款样式。

布局唯一参数源为 [layout.json](layout.json)，构建生成 `layout.lua`，预览与 Lua UI 使用同一配置：

| 区域 | 参数 |
| --- | --- |
| 时钟 | 原创 6×14 点阵，PNG/控件 90×232，x=8/116/226/334，y=68..300，约占屏幕上方 3/5 |
| 血糖 | 原创稀疏 5×7 单点笔画，数字 40×56、小数点 12×56、间距 4 px，y=352；整体按实际宽度自动居中，未用槽隐藏 |
| 原始时间 | 左侧 y=365、28 px、亮色 `#e9f2f8`，过期另起一行 `OLD` |
| 趋势 | 右侧 y=353、54×54 图形箭头 |
| 日期/电量/心率 | 沿用原布局，电量与心率为图标加文本 |

小时白色 `#f5f5f5`、分钟橙色 `#ff682b`，无冒号。血糖数值及趋势箭头按下面的用户自定义分段同步着色；无单位及曲线，时钟/血糖均不依赖字体轮廓。

**布局已实机确认，动态配色已安装并通过桌面边界验证。** 当前手机 APK 为 0.1.11 / code 12，RPK 沿用 0.1.8 / code 9，表盘沿用 0.1.10，已确认的布局和配色不变。单款 ID `8670260101` 已覆盖成功，通知图标也已确认正确。历史短锁屏自然更新不能外推为 Home 后或长期后台通过；后续确认 HyperOS Greezer 曾冻结手机进程，0.1.11 已完成恢复补传及两个镜像持续后台的自然周期文件导出；后一轮屏显待用户确认。Mi Fitness 开发授权 `designer_license` 仍返回 HTTP 404，实际安装沿用本地 SPP。参见 [后台排查](../docs/background-running.md)、[验证记录](../docs/validation.md) 和 [接续任务](../docs/HANDOFF.md)。

## 用户自定义显示颜色

按表盘的一位小数有效显示值 `v` 分段，数值和趋势箭头使用相同颜色：

| 显示值范围 | 新鲜读数颜色 |
| --- | --- |
| `3.9 <= v <= 7.8` | 紫色 `#924ff7` |
| `7.8 < v <= 12.0` | 黄色 `#ffd60a` |
| 其余有效值 | 红色 `#ff453a` |

边界 `7.8` 为紫色、`12.0` 为黄色；小于 `3.9` 或大于 `12.0` 为红色。旧数据仍显示原始时间与 `OLD`，数值和箭头在各自色系中变暗，不把旧读数改成新鲜读数。这是用户自定义的显示分段；不改变数据、提醒或告警逻辑。配色升级当时保持手机 APK 0.1.10 和 RPK 0.1.8 不变；当前手机 0.1.11 的后台修复仍沿用相同表盘配色与协议。动态配色版已通过 SPP 覆盖当前 ID `8670260101`，恢复默认启用状态及原通知监听后卸载临时安装器。三色、边界及过期分支已完成桌面测试；此前用户目视确认的是相同布局的静态紫色版，本次未额外确认真实数据下的颜色分段切换。

[配色预览](preview-colors.png)使用合成示例，供比较三种颜色及旧数据样式，不是实机血糖截图。

## 构建与测试

在仓库根目录运行：

```sh
python3 -m venv .toolchain/watchface-venv
.toolchain/watchface-venv/bin/pip install -r watchface/requirements.txt
.toolchain/watchface-venv/bin/python watchface/test_frame.py
.toolchain/watchface-venv/bin/python watchface/test_ui.py
.toolchain/watchface-venv/bin/python watchface/build.py
```

另需 Node.js 测试真实 JS 导出兼容性。构建使用 Pillow；时钟/血糖来自原创点阵，Barlow 仅用于预览文字及 unknown 问号，Lupa 仅用于桌面 Lua 测试。不依赖 Windows、EasyFace 或官方编译器。

输出位于忽略的 `watchface/build/`：

- `ottai-minimal-watch6.bin`：Ottai Ultra Lua 容器，ID `8670260101`。
- `ottai-minimal-watch6.zip`：Mi Fitness 内部开发入口封装，不是商店发布包。
- `preview-example.png`：合成布局预览，不是实机截图。
- `manifest.json`：ID、尺寸、体积和 SHA-256；另含生成素材及 `layout.lua`。

选择器的血糖/时间使用 `--` 与 `--:--` 占位，设备只显示合法文件读数，不把合成预览当实时数据。

## 数据更新

Vela 应用接收合法帧后，通过 `system.file` 写入双槽文件；Lua 表盘只读这些文件。格式和校验规则见 [数据协议](../docs/protocol.md)。发现更旧、损坏或未写完整的文件时保留最后合法读数及其测量时间。

表盘创建、亮屏和页面恢复时检查文件；亮屏且可见期间每 15 秒检查小文件，息屏或离开表盘后暂停该计时器。不轮询传感器，不用静音音频或定位保活。电量与心率通过 `dataman` 订阅，缺少有效值时显示占位。

**文件读取不等于后台更新已打通。** 实测表端应用隐藏后的两轮被动发送没有对应 ACK 或文件回执。现有策略先发送，8 秒未取得完整身份的文件确认才短暂唤起同步页，写入成功后退出；手机“表盘自动同步”新安装默认关闭。历史 0.1.8 两轮短锁屏约 9.8/9.7 秒并有用户屏显确认，只能证明这两轮连通与返回，未先确认 Home 后的后台状态。本轮 0.1.10 第一次由用户打开手表应用才导出，只有第二次自动完成，不能记两轮自动通过。

手机 0.1.11 的新读数/发送尝试有每次至多 20 秒 CPU 窗口，当前完整身份导出即提前释放；60 秒唤起冷却只限制相同身份，新测量或同时间更正不被旧身份挡住。它不改变文件格式，也不能解冻厂商冻结。已完成恢复补传及两个镜像持续后台的自然周期文件导出；后一轮屏显待用户确认，实际省电设置、验收标准及边界见 [后台排查](../docs/background-running.md)。它仍是必要时自动短暂打开应用后返回的策略；其他页面影响、断连恢复、长期稳定性、AOD 和耗电尚未完整验收。真实趋势目前只验证到水平箭头，斜向等方向仅完成映射测试。

0.1.8 的导出回执以 `sourceAt|规范数值|原始趋势` 的完整 `frameKey` 匹配当前读数，区分同时间的数值/趋势更正。文件发布串行执行，只保留最新待发布帧；旧完成不会越过新帧确认或触发退出，已写同身份可复用确认。自动同步会话绑定完整身份，设备延迟启动时仍保留返回标志。新合法帧先取消旧退出定时器，最新写入完成后重新安排，退出前再次核对当前身份；离页清理返回意图。

## 安装入口与验收

当前手机 APK 见 [0.1.11 发布目录](../releases/0.1.11/README.md)；表盘 BIN/ZIP 沿用 [0.1.10 发布目录](../releases/0.1.10/README.md)，本次无需重装；RPK 继续使用 [0.1.8 发布目录](../releases/0.1.8/README.md)中的 0.1.8，不重复分发。临时安装器 0.1.4 / code 5 位于 0.1.10 目录。先分别核对校验和，两端包名与证书保持一致即可，无需同版本号。本轮临时安装器 0.1.4 已卸载并清除手机端私有凭据；日常同步只需要原有镜像和 Mi Fitness 通道。

先完成 [安装文档](../docs/install.md) 的工具链与签名配置，然后可打开开发入口：

```sh
. .toolchain/android.env
python3 tools/open_installer.py --serial SERIAL --watchface watchface/build/ottai-minimal-watch6.zip
```

Mi Fitness 开发入口在授权接口 HTTP 404 处失败；打开页面、解压成功或请求授权均不表示安装完成。[本地 SPP 临时安装器](../tools/spp-installer/README.md) 已完成正常认证、100% 上传及断开，用户也已确认修正 Lua 入口后的表盘正常绘制。本轮用安装器 0.1.4 的 `replace` 覆盖 ID `8670260101`：只删除当前 BIN 目标，独立查询确认删除后再安装，不删除其他表盘、不解绑。安装器另外允许预留 ID `8670260102`，供未来不同风格扩展；本轮不发布、不安装该 ID。只能使用用户自己设备的合法配对密钥，密钥不得进入仓库或日志输出。

曾出现“上传完成但黑屏”：容器中上游命名为 `sentinel` 的字段实际是 Lua anchor payload 的资源索引，默认 `n-1` 在本项目指向趋势 PNG，而 `lua/main.lua` 当时位于索引 14。构建现在按文件名确定 `main_index`，打包后解包断言确实指向 `lua/main.lua`，不能把 14 当作以后固定入口。

暂停蓝牙桥接后须恢复 Mi Fitness 与镜像的原运行状态及原有通知授权；尤其 `disable-user` 可能清除通知访问。恢复及正常重启后必须实际核对默认启用状态、原通知授权及监听绑定，不能仅信 `pm` 输出；再确认最新自然 Ottai 通知进入镜像，不能用恢复旧缓存通知的回执作为新周期验收。

新环境基本验收应复验：安装成功且其他表盘可回退；字体和数值目视正常；手机先 Home 确认为 FGS 后台，再锁屏，至少两个 Ottai 自然周期不手动打开两端镜像，核对通知未积压、自动唤起、完整身份文件确认、测量时间推进及表盘正常返回。当前设备的布局与通知图标已有确认，历史短锁屏通过不替代这项严格验证；手机 0.1.11 已完成恢复补传及两个镜像持续后台的自然周期文件导出；后一轮屏显待用户确认。新环境也应复验大时钟、配色、稀疏血糖居中和左时间/右箭头。旧数据标记、断连与休眠恢复、长按换表盘及其他页面行为仍需继续验证；当前没有单独 AOD 子工程，息屏显示、长期稳定性及耗电尚未完整验收。
