# Health Connect activity channel (0.4.0)

The single-user service reads the adult device's optional, user-authorized Health Connect snapshot through Android. It does not access Mi Fitness private storage, routes/GPS, titles, notes, accounts or identifiers beyond Health Connect record IDs. Only `DataOrigin=com.mi.health` is accepted. `originApp` describes the installed Mi Fitness version at synchronization, not necessarily the version that originally created every record. Device metadata is retained; one source package does not prove that all records came from a watch.

## Atomic native snapshot contract

`POST /api/v1/activity`, `Content-Type: application/json`, device **INGEST_TOKEN** only. Read and analysis capabilities cannot write. All seven fields are required:

```json
{"source":"health_connect","syncedAt":1794280000000,"windowStart":1794107200000,"windowEnd":1794280000000,"status":"available","readableKinds":["exercise","heart_rate","steps"],"records":[]}
```

The example is synthetic. Optional top-level `originApp={packageName:"com.mi.health",versionName?:string,versionCode?:integer}` is preserved. Each record has `id`, `kind`, `origin`, `startAt`, `endAt`, `modifiedAt`, `recordingMethod` plus the kind-specific field:

- `exercise`: integer `exerciseType`.
- `heart_rate`: `samples:[{time,bpm}]`, including valid empty lists and zero-duration native records. Original samples are preserved and canonically sorted by `(time,bpm)`. Duplicate and conflicting equal-time samples are allowed; no invented sensor fusion.
- `steps`: integer `count`; original interval is preserved. No distribution of a daily total to minutes.
- `sleep`: no additional fields; a positive-length native sleep-session interval. Titles, notes and sleep stages are not accepted or transported.

Optional record `startOffsetSeconds`/`endOffsetSeconds` (UTC ±18h) and `device={manufacturer?,model?,type?}` preserve native provenance. Timestamps are integer epoch milliseconds. Source starts, modification times and actual HR samples retain the 90-second future tolerance against server time. Native interval `endAt` may be a future day/container boundary, bounded by the 31-day maximum interval and `syncedAt + 31 days`; this metadata never creates future observations. Sessions extending beyond the observation cutoff are explicitly right-censored (`endBeyondObservationWindow`, `endCensored`, `observedEndAt`), and no post-session glucose effect is computed until an end is observed. HR is finite, >0 and <=300; this is an input sanity bound, not a health classification. Counts, IDs, descriptions and enum fields are bounded; unknown fields, routes and notes are rejected. One request is at most **4 MiB / 10,000 records / 100,000 HR samples**, with a maximum 31-day read window. The Android collector currently reads 48h. If limits or any page fail, do not upload a truncated snapshot. There is no chunk/staging protocol.

**Native framework `readRecords` is START-time scoped:** snapshot members have `windowStart <= startAt < windowEnd`; `endAt` may lie outside the query. Within one transaction, reconcile only old records whose **startAt** is in that same window and whose kind is in `readableKinds`. Thus an omitted cross-boundary record starting earlier is retained, not falsely deleted. Dashboard and report queries use actual interval overlap (and preserve instantaneous records). First-time reads can miss a long-running record started before the query; successful query windows do not establish complete wear/sample coverage. See the [framework RecordHelper implementation](https://android.googlesource.com/platform/packages/modules/HealthFitness/+/refs/heads/main/service/java/com/android/server/healthconnect/storage/datatypehelpers/RecordHelper.java).

Whole snapshots validate before mutation. Same `syncedAt` and canonical body is idempotent; same timestamp/different body is `409 snapshot_conflict`; older uploads return `200 status=stale_ignored`. Newer collections carrying an older `modifiedAt` cannot regress an existing source revision. Empty successful snapshots reconcile deletions only within the bounded read scope. Records outside that scope remain historical until a later successful read covers them. `permission_denied` and `unavailable` snapshots must have empty readableKinds/records and retain historical data. Partial permissions reconcile readable kinds only.

Success: `{ok:true,serverAt,accepted,inserted,updated,deleted,unchanged,status}` where status is `accepted|duplicate|stale_ignored`. Invalid activity is 400; a write capability is required before reading any body. Transport/body length/time limits remain enforced.

## Dashboard and analysis

`dashboard.activity` includes source/origin/version, availability/readableKinds/staleness, last sync/success, requested/source windows, original exercise periods, step intervals, HR summaries, and limitations. `queryCoverageMinutes` is the union of successfully queried **start-time** windows per kind, never time spent moving or continuous HR coverage. A denied/missing/stale stream is not sedentary behavior.

Public payload is bounded: at most 128 compact exercise sessions, 288 original step intervals, and 288 explicitly labeled five-minute HR **sample summaries** (mean/min/max/count/first/last actual timestamp), with truncation flags. These summaries do not create interpolated measurements. Equal simultaneous HR values collapse for summaries; conflicting simultaneous values are excluded from fusion and flagged; raw records remain in storage. Potentially overlapping step intervals, including duplicates within Mi Fitness, are flagged and their total is null. Any zero-duration step record also suppresses the total because its counting interval is unknown; two same-time phone/watch point totals must never be summed. Edge-crossing intervals are not prorated. Short intervals <=15min are retained as activity clues; longer intervals remain `coarse_total`; zero duration is `instant_count`. Those are product display categories, not validated exercise thresholds.

`exerciseTypeLabel` is a bounded native-framework label mapping, verified against the public `ConstantValue` entries in the official Android API 35 `android.jar` (`android.health.connect.datatypes.ExerciseSessionType`), not the incompatible Jetpack values. For example native walking=53, running=33, biking=4, wheelchair=56. Unmapped values remain `其他运动（类型代码X）`; neither clients nor the model guess type/intensity from a raw code. Source: [native framework API](https://developer.android.com/reference/android/health/connect/datatypes/ExerciseSessionType).

AI context also includes `heartRateTimeline` for both 24h periods even when there is no exercise session. At most 96 rows summarize **observed samples in 15-minute bins**, with explicit columns: bin start/end minutes before that context's period end, first/last real sample minutes before end, sample mean/min/max bpm, sample count. Rows are chronological; because these are minutes *before* end, earlier/start values are >= later/end values. Each prior/current context uses its own periodEnd. Missing buckets stay absent, and arithmetic sample means are not time-weighted wear or continuous heart rate. First/last exact sample epoch and full Shanghai local time, plus age at report time and age at period end, describe sparsity/staleness. Session HR statistics use the same real, deduplicated/non-conflicting points and give null mean/min/max at zero samples; they do not classify intensity. A dense synthetic stress fixture (365 days glucose, two 1 Hz HR days, 24 sessions and 288 short step intervals per day) verifies the entire serialized Responses request remains below 256 KiB. Repeated per-session glucose labels/reference boilerplate are omitted; actual weighted core statistics and coverage remain intact.

Reports receive immutable current and previous 24h activity snapshots. Each recorded session includes deterministic full `startLocal`/`endLocal` ISO datetimes with `+08:00` and explicit `timezone=Asia/Shanghai`, alongside the original epoch timestamps; the model does not need to convert epoch times. Original exercise sessions are aligned with glucose for **before 30min / during / after 60min**, each retaining weighted glucose metrics and missingness; these are descriptive product windows, not proven biological effect windows. Sessions at report boundaries have clipped windows/null where no window exists. Candidate excursion overlaps are descriptive only. HR alone does not infer exercise; steps without a session are only activity clues. No wearable coverage, intensity zone, meal or causal effect is invented. Only two days of activity context are currently provided, so the model must not claim multiweek activity trends; existing longer-term glucose comparisons remain available.

Manual report identity now includes activity content/availability/query coverage, so corrected/deleted activity can become a new snapshot while unchanged read timestamps do not consume additional model requests. The durable 30min cooldown still applies. Activity is captured before the manual job starts; later incoming changes cannot mutate a queued job. Fixed previous-calendar-day scheduled reports retain their own independent identity and period.

The conservative prompt uses the [ADA physical activity position statement](https://doi.org/10.2337/dc16-1728), [ACSM 2022 consensus](https://pmc.ncbi.nlm.nih.gov/articles/PMC8802999/) and existing CGM methodology. Type, intensity, timing, food, medication and population affect responses; observed association does not prove exercise causation, unhealthy eating or hormone/β-cell change. Diabetes-population exercise prescriptions are not automatically applied to an adult without a diagnosis. The wider feasibility/source discussion remains in [ACTIVITY_INTEGRATION_FEASIBILITY.md](../docs/ACTIVITY_INTEGRATION_FEASIBILITY.md). Android [raw-data guidance](https://developer.android.com/health-and-fitness/health-connect/read-data) recommends aggregate APIs for cumulative totals to prevent multi-source double counts; this channel deliberately preserves raw source-specific intervals and does not claim a fused total when ambiguous.

## Verification

`python3 -m unittest server.test_server server.test_activity -v` uses synthetic local temporary databases and a local HTTP server, with no provider/model call. It covers source/field/time/body bounds, collector metadata and native zero/empty/unsorted/duplicate HR edges, idempotence, stale/conflicting snapshots, corrections/deletions, start-time/cross-boundary scope, partial/revoked permissions, overlapping/coarse steps, 86,400 HR samples compacted below the existing 512 KiB client limit, manual snapshot updates and queued-snapshot immutability. Actual Mi Fitness output/granularity and screen-off background synchronization still require user consent and real-device checks; no sample-data fixture is put in the live database.


## Hybrid step fallback (0.4.1)

After the on-device Mi Fitness sync and Health Connect UI check confirmed that heart rate was being written but Steps were absent, the optional Xiaomi system-provider step channel was added. Heart rate and recorded exercise **continue through Health Connect**. No private Mi Fitness database, GPS, new sensor service or custom background pedometer is used by this server channel.

`POST /api/v1/activity` also accepts `source="phone_steps"`, record `origin="com.miui.rom"`, `readableKinds=["steps"]` only. The same complete START-time snapshot and bounds apply. Optional native `providerMode` is an integer 0–1000 retained without inventing a type/intensity interpretation. `originApp.packageName` must match `com.miui.rom`. The collector emits `revisionBasis="collection_time"`: provider rows lack a last-modified timestamp, so `modifiedAt` records when this semantic revision was observed. Repeated reads changing only that collection timestamp keep the stored semantic record and AI identity unchanged; changed count/interval/provenance is a real revision. HTTP snapshot retry digests still compare the full normalized request. Each source has independent state and a source-scoped reconciliation transaction.

An atomic migration converts records to `(source,record_id)` and query coverage to `(source,kind,start_at)`, preserving existing HC bodies, future-ended native containers, all CGM readings/revisions and fixed/manual reports. Back up the production SQLite database consistently before deployment. Tests reopen a legacy database twice and verify preserved health records, CGM correction audit, report bodies and indexes.

For each requested window, HR and exercise select HC. Steps select fresh (under 30min), authorized HC actual records first; if HC has only coarse records and fresh phone data has real intervals <=15min, choose phone. Fresh phone records also replace unavailable/stale/revoked HC step access. If neither is fresh/readable, retain an explicit cached choice; no fake zero or hidden merging. Future-start records cannot influence this choice. Daily/rolling analysis takes one **two-day snapshot** and carries the same chosen step source into both 24h contexts; it does not reselect the prior day independently. Dashboard queries its own rolling24h window. The phone and HC totals are never added. Coarse, overlapping, instantaneous and edge-crossing step restrictions continue to apply within the selected source.

Schema1-compatible fields add `sourceByKind={exercise:"health_connect",heart_rate:"health_connect",steps:"health_connect"|"phone_steps"}`, `sourceByKindReason`, `sourceStates` (each source's status/readableKinds/stale/last sync/success/version/revision basis), and `kindAvailability` (selected source, readable/stale, record bounds, actual HR first/last sample). The aggregate `source` is `mixed` when both channels are selected; its `origin` and `originApp` are null, while records and sourceStates preserve actual provenance. Summary fields identify each type's source; step counts/intervals contain only the selected step channel. `lastRecordEndAt` is source container metadata, not proof of last sampling; `lastSampleAt` is the actual observed HR time. Per-kind state prevents a new phone upload from masking an old or revoked HR stream.

Phone steps are only activity clues when the phone was carried and the system recorded them. Missing steps cannot imply sedentary behavior, absence of exercise or physiological change. Source/granularity changes are not valid activity/clinical improvements. The provider API reference is [Xiaomi HyperOS step data](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=1603); permission, device support, raw interval quality and background delivery are separately verified by the Android/device task.


## Complete provider-batch step context

Public dashboard `stepIntervals` now selects the **latest** 288 records, with `stepIntervalsSelection`, `stepIntervalsTruncated` and complete `stepIntervalTotalCount`. Aggregate source statistics still use every selected record. AI receives at most 32 latest short raw examples and an explicit examples/truncation label; a complete `stepTimeline` uses all selected records, with <=96 start-time-grouped 15-minute bins per day. Each row includes bin bounds, earliest native start/latest native end, raw count sum, original row count and cross-bin row count. Relative times use that context's own periodEnd. Records beginning before the window are kept in explicit outside-start-window counts/sums rather than moved into a false bin. Global overlap, cross-period, future-end, coarse and instantaneous flags distinguish raw count sums from an independent complete-window step total. A 352-record synthetic regression confirms both the latest public records and all counts remain available to analysis.

Provider bounds are **batch boundaries**, including potentially extremely short intervals. They do not establish continuous walking time or when each individual step occurred. Never divide a raw count by batch duration to infer cadence/speed/intensity, interpolate continuous activity, or prorate a coarse/cross-period batch. A rolling24h sum must not be compared directly with a calendar-today total. `recordWindowOverlapEndAt` is clipped source-container metadata; HC HR `lastObservedEndAt`/`lastSampleAt` are the actual last usable HR sample, preserving sparse-sample freshness even when the native container ends tomorrow.


## HC active energy context (0.4.2)

A fourth optional HC-only kind, `active_calories`, carries numeric finite `energyKcal` in **kilocalories**, product sanity bound 0–100000 per native interval, plus the same original interval/metadata/UTC offsets/device fields. Only `ActiveCaloriesBurnedRecord` is accepted; no TotalCalories/BMR or dietary intake channel is added. The native platform SDK exposes small calories, so the Android adapter converts `getInCalories()/1000`; the AndroidX converter/unit definitions and a 1000cal→1kcal test verify the factor. The API unit remains energyKcal. Existing source-scoped SQLite tables accept the new kind without another migration. HC `readableKinds` can have four entries; `phone_steps` remains strictly steps-only. Missing/revoked energy access is missing, never zero.

`sourceByKind.active_calories` is always `health_connect`; per-kind availability/version/provenance remain separate from phone steps. Summary adds `activeCalorieRecordCount`, nullable `rawActiveKcalSum`, nullable `observedActiveKcal`, `potentialActiveCalorieOverlap` and `activeCalorieCoarseRecordCount`. Observed total is available only with readable/fresh source, actual records, no overlap/instantaneous ambiguity, and every interval fully inside the observed window. Raw sums retain cached or overlapping estimates with explicit flags; they are not automatically an independent complete-window total.

Both AI periods receive complete `activeCalorieTimeline` with at most96 native-start-grouped 15-minute bins per day, original earliest start/latest end, raw energy sums, row/cross-bin counts and overlap/cross-period/future/coarse/instant flags. Out-of-start-window records stay in separate summary fields; no prorating or synthetic continuous curve. At most32 latest original `activeCalorieExamples` preserve device provenance and have an explicit truncation flag. Public `activeCalorieIntervals` likewise keeps the latest32 and total/truncation metadata. Dense tests cover1440 energy intervals/day while retaining2-day1Hz HR,365-day glucose history,24 sessions/day and288 step records/day; the full Responses request stays below256 KiB and public dashboard below512 KiB.

These are **estimated active energy**, not precise calorie balance, metabolic rate or evidence of specific exercise intensity. Device energy algorithms can use the same HR/motion measurements already in the report, so agreement is not independent corroboration and must not increase confidence twice. The Mi Fitness source package does not establish watch provenance; source device is unknown unless its metadata supports a specific attribution. Records can supplement phone-not-carried periods only when their actual device/source supports that interpretation. Never convert energy to steps, exercise duration or an intensity prescription, and never interpret absent/zero readings as lack of activity. Existing non-causal CGM analysis limits continue to apply.


## Shared public activity plot

`dashboard.activity.plot` is a complete, bounded presentation layer shared by phone and Mac. It has `periodStart`, `periodEnd`, `intervalMinutes=15`, `steps` and `activeCalories` flat arrays (at most96 bins each). A step bin contains `startAt`, `endAt`, raw `count`, `recordCount`, `firstRecordStartAt`, `lastRecordEndAt`, `crossBinRecordCount`, selected `source` and `potentialOverlap`. Energy bins use the same fields with `energyKcal` instead of count. Original source intervals are grouped by native start time, never uniformly spread, interpolated or treated as an exact15-minute occurrence amount.

The additive `activeCalories30m` array uses the same energy row shape, but groups eligible native intervals of `0 < duration <=30min` by their start into at most48 half-hour bins per24h. `activeCalories30mIntervalMinutes=30` declares this cadence; `activeCalories30mTruncated` bounds unusual longer windows, and `activeCalories30mOmittedRecordCount` counts unique raw records excluded from this array (including any trimmed groups), without double-counting a future-ended cross-period record. Current clients prefer this array when present, even if empty, and fall back to the old15m array for older servers. The original arrays and counters remain unchanged so old strict15m clients continue to decode the dashboard. This displays source records of approximately30minutes without splitting or prorating them into fake15-minute observations. Source start grouping is still descriptive, not exact half-hour occurrence timing; original first/last record times and cross-bin flags remain explicit. Full AI timelines and their15m start-group/coarse annotations are unchanged.

Only native intervals with `0 < duration <=15min`, a start in the requested window and an end no later than the observation cutoff enter plot bins. Coarse summaries, instantaneous records, records crossing the observation window and future-ended records do not become bars. Separate coarse/instant/cross-period/future-end record counters, truncation booleans, `meaning` and `limitations` explain absent data. Complete AI timelines and raw source summary values retain those records with their original flags. In particular a daily active-energy summary cannot create a false midnight15-minute peak. A352-record step regression proves that grouping uses all eligible records, including older records omitted from the latest288 raw display list. A daily/short/cross-bin/future energy regression proves that only the eligible short batches appear in the plot.

The plot's step channel still contains only the chosen HC/phone source, while energy is HC-only. HR remains a separate5-minute observed-sample summary with actual first/last sample times. Clients should use separate units/axes or small activity tracks; they must not turn energy/steps into glucose units, inferred cadence/intensity or continuous movement. Empty tracks mean no eligible plot intervals, not zero activity or proof of a missing sensor. Sample/provider metadata remain source-specific; preserve the weak/estimated nature of the activity context.


## HC sleep sessions and observed glucose context (2026-11-11)

The fifth optional HC kind is `sleep`, sourced only from `com.mi.health` through native `SleepSessionRecord`. It uses the common original interval/metadata fields with `startAt < endAt`, and adds no text, stage or inferred score. Existing source-scoped tables need no migration. `readableKinds` may now contain five entries; older clients omitting sleep keep their original behavior. An unavailable or partially authorized snapshot retains cached sleep records, and only a successful snapshot explicitly readable for `sleep` may reconcile its in-window deletions/corrections. `sourceByKind.sleep` remains `health_connect`, with separate `kindAvailability.sleep` and query coverage; successful reads are not sleep coverage.

Public `activity.sleepSessions` contains up to the latest128 records, preserving `id`, `origin`, original `startAt/endAt`, `recordingMethod` and optional `device`. `sleepSessionsTruncated` and `sleepSessionTotalCount` explain bounds. Clients clip the visible intersection with the chart window/current time. Overnight and earlier-started overlapping records keep their original bounds and are not deleted by a newer narrower START-scoped snapshot. Cached data can remain after read permission is absent; per-kind readability/staleness must distinguish this from a fresh source. Existing `exerciseSessions` and native exercise labels remain independent of sleep and manual lifestyle markers.

Both rolling/fixed brief contexts and detailed contexts receive up to32 actual `sleepSessions` per period, with provenance, Shanghai timestamps, `observedStartAt/observedEndAt`, `endCensored` and `glucoseDuring` time-weighted metrics/coverage for that intersection. A session continuing beyond a report cutoff exposes only the cutoff as AI `endAt/endLocal`; AI-only `kindAvailability.lastRecordEndAt` is also clipped and flagged `recordEndCensored`, preventing the metadata side channel from revealing a later wake time. The public chart payload still preserves the native interval. Missing glucose stays missing; no sleep interval or stage is inferred from HR, clock time or manual sleep/wake markers. Brief and detailed exercise observations use clipped session ends and observed bounds, before30min/during/after60min CGM metrics; censored sessions have no post-exercise window and cannot reveal a future endpoint. `intervalEndMeaning` labels the brief-context endpoint semantics explicitly.

`summary.potentialSleepSessionOverlap` (and the detailed context counterpart) flags overlapping native sessions. They are retained separately, not added into a total sleep duration. Sleep-session windows may contain awake portions: interval length is not total time asleep, sleep efficiency, sleep quality, or a diagnosis. `lifestyle.sleepPairs` remains explicitly user-reported and separate; no automatic record overwrites, fabricates or confirms a manual event. No extra model call or schedule is introduced by sleep collection.

Synthetic tests cover positive/native interval and privacy validation, old-client/partial/revoked permission retention, corrections/deletions, overnight START-window edges, observed CGM gaps, public/context bounds, overlap flags, fixed-cutoff future exclusion and separate manual sleep pairs. No fixture is uploaded to production.
